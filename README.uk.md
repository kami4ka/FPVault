[English](README.md) | Українська

Прошивка бортового FPV-відеореєстратора з відкритим кодом для Allwinner
F1C200s.

Записує аналогову CVBS-камеру на SD-карту як MJPEG-in-AVI з майже нульовим
навантаженням на CPU: кожен етап конвеєра — апаратний периферійний блок, а
ядро ARM926 лише диригує.

![Конвеєр FPVault](docs/img/pipeline.uk.svg)

- **Bare metal** — без Linux і без RTOS. Один бінарник, один головний цикл,
  кілька переривань.
- **Апаратний MJPEG** — Video Engine у F1C200s кодує до 1280×720@30
  (даташит §2.5); аналогові кадри D1 (720×480/576), які записуються тут,
  вкладаються з великим запасом.
- **Керування з польотного контролера** — реалізовано бік пристрою
  протоколу RunCam Device Protocol v1.0, тож Betaflight, INAV та ArduPilot
  вміють запускати/зупиняти/перемикати запис «з коробки». Пін GPIO/RC-PWM —
  запасний варіант без FC.
- **Стійкість до втрати живлення за побудовою** — автозапис за наявності
  відеосигналу, 5-хвилинні сегменти, попередньо виділені файли, періодичне
  оновлення заголовка AVI: висмикнута батарея коштує щонайбільше останньої
  секунди поточного кліпу.
- **Лише відгалуження для запису** — DVR під'єднується до лінії камери
  паралельно і нічого не додає у відеотракт. Відвід високоомний: вхід DVR
  НЕ повинен термінувати лінію; рівно один резистор 75 Ом на лінію, і його
  місце — на боці VTX/дисплея.
- **Вбудований USB-кардридер** — під'єднайте плату до комп'ютера, і
  SD-карта змонтується як USB-накопичувач ("FPVault SD Card"): карту виймати не
  треба, зайвих файлів на ній не з'являється. Від живлення, що не є
  комп'ютером (зарядка, 5 В від FC), плата натомість записує.
- **Оновлення прошивки тим самим USB-кабелем** — плата водночас є
  стандартним DFU-пристроєм; `dfu-util -D fpvault.bin` стейджить, перевіряє,
  прошиває NOR і перезавантажує. Без кнопок, без UART-адаптера, без файлів
  на карті.
- **Застосунок для комп'ютера, якому нічого не треба встановлювати** —
  [FPVault Desktop](desktop/README.uk.md) імпортує й лагодить кліпи,
  проставляє їм справжні дати, яких плата без годинника дати не може,
  склеює або експортує сесію, відтворює покадрово й прошиває через USB.


## Стан проєкту

Ранній етап. Віхи:

- [x] M0 — каркас: збірка, завантаження через U-Boot, консоль, світлодіод,
      watchdog
- [x] M1 — апаратний JPEG на Cedar VE: **2,9 мс/кадр на кремнії** (VE 1663)
- [x] M2 — SD 4-біт + FatFs: **7,8 МБ/с стабільно, 64 МБ звірено побітово**
- [x] M3 — живе захоплення → кодування: **повні 29,97 fps, конвеєр в IRQ,
      0 втрачених кадрів**
- [x] M4 — крешостійкий запис AVI з правильним кольором (TVD 4:2:0 → NV12)
- [x] M5 — автономний рекордер: автозапис за сигналом, 5-хв сегменти,
      іменування DCF, політика зникнення сигналу, LED-індикація станів
- [x] M6 — RunCam Device Protocol наживо на UART1 (Betaflight/INAV/
      ArduPilot) — *перевірено на стенді фаз-тестами; сесія зі справжнім FC
      попереду*
- [x] M7 — витривалість і загартування ін'єкцією відмов: **80 хвилин
      безперервного запису, 16 послідовних 5-хв сегментів, 144 000
      кадрів, 0 втрат, кожен JPEG перевірений**; крешостійкість доведена
      на 8 реальних раптових зникненнях живлення (кожен кліп
      відтворюється до 1 кадру перед обривом); ін'єкція затримок SD
      пройдена. Прогін також породив errata щодо живлення в
      docs/HARDWARE-ERRATA.uk.md — стендовій платі знадобився об'ємний
      конденсатор біля слота SD, щоб пережити м'які джерела.
- [x] M8 — автономне завантаження зі SPI-NOR: від подачі живлення до запису
      за ~5 с (U-Boot із вшитим bootcmd у NOR 0, прошивка в NOR 0x100000)
- [x] M9 — USB mass storage: під'єднайте до комп'ютера — карта монтується
      (стек CherryUSB на контролері MUSB, USB 2.0 High-Speed)
- [x] M10 — **FPVault Desktop**, застосунок-компаньйон у `desktop/`:
      імпортує кліпи й лагодить ті, які обірвало зникнення живлення,
      проставляє їм справжні дату й час, склеює або експортує сесію,
      відтворює їх покадрово й оновлює прошивку через USB з анімованими
      підказками для того, що вимагає рук на платі
- [x] M11 — **USB-камера**: під'єднана до комп'ютера плата є вебкамерою так
      само, як і кардридером, і передає той самий MJPEG апаратного
      кодування, який пише рекордер. Виміряно 30 fps, 0 втрат, ~690 КБ/с,
      і карта весь цей час змонтована та читається на повній швидкості.
      Вмикати нічого не треба: потік UVC ініціює хост, тож він починається,
      коли застосунок відкриває камеру

Подайте живлення на плату зі вставленою картою — і вона записує: без
хоста, без команд.

Набір тестів для хост-машини: `make -C tests/host` (крос-тулчейн не
потрібен).

## Апаратура

### Плата FPVault v1

![Плата FPVault v1](docs/img/board-v1.jpg)

Спеціально спроектована плата DVR, двошарова, чотири монтажні отвори.
Стоїть у розриві відеолінії: `CVBS_IN` від камери, `CVBS_OUT` на VTX.
Байпас аналоговий — відеопідсилювач THS7374 живить ключ TS5A3153, який
передає камеру прямо на вихід без участі прошивки (PE4 у стані підтяжки),
а той самий підсилювач відгалужує картинку для декодера F1C200s. Живлення
з USB-C або з майданчика `5V_IN` через мультиплексор TPS2116; майданчики
`RX`/`TX` виводять UART0. Те саме ядро F1C200s + 16 МБ NOR W25Q128 +
microSD + EA3059C, що й на платі розробки, плюс SW1 (скидання) і SW2 (FEL,
див. [docs/BRINGUP.uk.md](docs/BRINGUP.uk.md)). Два екземпляри оживлені й
записують; знахідки — в [docs/HARDWARE-ERRATA.uk.md](docs/HARDWARE-ERRATA.uk.md).

Схема: [PDF](docs/hw/fpvault-board-v1-schematic.pdf) ·
[PNG](docs/hw/fpvault-board-v1-schematic.png)

### Плата розробки

![плата розробки](docs/img/dev-board.jpg)

Універсальний модуль F1C200s, на якому все було оживлено спочатку: F1C200s
(під радіатором), SPI-NOR W25Q128, USB-C, microSD, піни CVBS `TV IN` і
гребінка `TV_OUT`, PMIC EA3059C. Його особливості — перша частина
[docs/HARDWARE-ERRATA.uk.md](docs/HARDWARE-ERRATA.uk.md).

## Збірка

Потрібні `arm-none-eabi-gcc` (перевірено з 14.2) і GNU make.

```sh
make            # build/fpvault.bin
make deploy     # надіслати на плату, що стоїть у промпті U-Boot (YMODEM)
make dfu        # оновити працюючу плату через USB (dfu-util)
```

Цикл розробки розраховує на U-Boot у SPI-NOR плати: `loady 0x80000000`,
потім `go 0x80000000` — `make deploy` (tools/loader.py) робить обидва
кроки. Послідовний порт за замовчуванням — `/dev/cu.usbserial-0001`;
змінюється через `make deploy PORT=...`. Консоль: 115200 8N1 на UART0
(PE0/PE1), однолітерні команди, `s` = стан, `r` = скидання.

## Апаратні вимоги

Будь-яка плата F1C200s із: входом CVBS на TV_IN, SD-картою на SDC0
(PF0–PF5, 4-біт), SPI-NOR на SPI0, консоллю на UART0. UART1 (PA2/PA3)
з'єднується з польотним контролером для керування RunCam. Обов'язково
64 МБ (F1C200s) — DMA-арена не вміщується в 32 МБ F1C100s.

## Підготовка картки

Прошивка не вміє форматувати картку — FatFs зібрано без `f_mkfs`, — тож
картка має приїхати готовою. Сама прошивка теж не пише на картку нічого,
крім кліпів, і очікує такої самої ввічливості у відповідь.

### Формат: FAT32 із MBR

| | |
|---|---|
| Файлова система | **FAT32**. exFAT вимкнено при збірці (`FF_FS_EXFAT 0`) |
| Розмітка | **Master Boot Record** або жодної. GPT не читається |
| Імена | 8.3, великими літерами; довгі імена вимкнено (`FF_USE_LFN 0`) |
| Обсяг | Будь-який у межах FAT32. Кліпи йдуть ~2,4 ГБ/год, тож 32 ГБ — близько 13 годин |
| Швидкість | Будь-яка картка Class 10 / U1. Запису треба менше 1 МБ/с; тракт дає 7,8 |

Формат важить найбільше для великих карток. Специфікація SD призначає exFAT
для SDXC — тобто для всіх карток понад 32 ГБ, — а FAT32 лише для SDHC. Тому
нова картка на 64 ГБ буде exFAT просто з упаковки, і плата її не змонтує.
Картки на 32 ГБ і менше зазвичай уже у FAT32 і придатні одразу.

macOS, де `diskN` — ваша картка зі списку `diskutil list`:

```sh
diskutil list                                          # знайдіть картку, уважно
diskutil eraseDisk FAT32 FPVAULT MBRFormat /dev/diskN
```

Linux, де `sdX` — ваша картка:

```sh
sudo parted /dev/sdX mklabel msdos
sudo parted -a optimal /dev/sdX mkpart primary fat32 1MiB 100%
sudo mkfs.vfat -F 32 -n FPVAULT /dev/sdX1
```

Керування дисками Windows не пропонує FAT32 понад 32 ГБ: скористайтеся
`format /FS:FAT32` з командного рядка з правами адміністратора або
відформатуйте картку на іншій машині.

### Зітріть старий завантажувальний блок

Ця пастка найболючіша, бо виглядає як мертва плата. BROM у F1C200s шукає
завантажувальний заголовок на SD-картці **раніше**, ніж звертається до
SPI-NOR. Тож картка, на якій колись був образ Allwinner — Armbian, образ
LicheePi, будь-що записане через `dd`, — перехопить завантаження, і плата не
запустить власну прошивку. Переформатування це не прибирає: заголовок лежить
у секторі 16, у проміжку перед першим розділом, якого файлова система не
торкається.

Плата вміє прибрати його сама. У консолі: `:M` — змонтувати, далі `:Z`:

```
[sd] partition 0 starts at LBA 2048
[sd] STALE BOOT BLOB FOUND (eGON at sector 16) - scrubbing
[sd] scrubbed sectors 16..47 - the card can no longer hijack boot
```

`:Z` відмовляється працювати, якщо перший розділ починається раніше за
LBA 48: тоді проміжку немає і сектори 16–47 належать файловій системі. Це ще
одна причина робити MBR, а не картку без розмітки — звичайна таблиця
розділів залишає цей проміжок.

### Тримайте на ній лише кліпи

На картці не має бути нічого, крім записів. Зокрема macOS пише
`.Spotlight-V100`, `.fseventsd`, `.Trashes` і файли `._` на будь-який том,
який монтує, тож картка після Mac неодмінно їх набере.

```sh
mdutil -i off /Volumes/FPVAULT                 # вимкнути індексацію Spotlight
touch /Volumes/FPVAULT/.metadata_never_index   # і не дати їй повернутися
mkdir -p /Volumes/FPVAULT/.fseventsd && touch /Volumes/FPVAULT/.fseventsd/no_log
defaults write com.apple.desktopservices DSDontWriteUSBStores -bool true
dot_clean /Volumes/FPVAULT                     # прибрати наявні файли ._
```

### Що плата робить сама

Вручну створювати нічого не треба. На першому ж записі прошивка сама будує
дерево DCF:

```
/DCIM/100FCDVR/FCDV0001.AVI
/DCIM/100FCDVR/FCDV0002.AVI
/DCIM/101FCDVR/FCDV0003.AVI     <- наступне ввімкнення, наступний каталог
```

Новий каталог на кожне ввімкнення групує кліпи за сесіями без годинника.
Номери файлів зростають монотонно на всій картці й ніколи не
перевикористовуються, тож два кліпи не можуть мати однакове ім'я навіть після
видалень: єдине джерело істини — сканування картки під час завантаження, а
отже нумерація сама відновлюється після заміни картки чи ручного прибирання.

На `FCDV9999` або каталозі `999` запис зупиняється, а не перезаписує щось, і
просить прибрати картку або переформатувати її.
